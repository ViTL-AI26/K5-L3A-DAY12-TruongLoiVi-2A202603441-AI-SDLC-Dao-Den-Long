# Retro v1.0.0

Across four phases, the most effective practice was treating the deterministic headless core as the product contract and keeping visual work outside it. Small scenario fixtures exposed fuel boundary and dawn float mistakes before release. AI assistance was useful for tracing old assumptions and drafting tests, but it also made plausible-looking Phase 1/2 expectations stale after later tickets; running the real harness caught those errors.

`AGENTS.md`, fixed-tick tests, JSONL fixtures, and `git diff --check` were the highest-value harnesses. The approach saved tokens by reusing the shared core rather than producing separate graphical rules. Estimated AI usage is the interactive coding-session allocation; no paid API calls or external generated assets were used. If repeating the project, I would create benchmark/soak/release entry points in Phase 1 and design the graphical menu/settings shell before feature phases.
